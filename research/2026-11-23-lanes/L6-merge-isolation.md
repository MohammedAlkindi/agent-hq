## Checkpoint 3 (13:20 real clock 13:17): landing mechanisms read from source/docs

- VERIFIED (docs): GitHub merge queue (docs.github.com "Managing a merge queue", read via fetch): each queued PR gets a `merge_group` run on a temp branch containing latest base + every PR ahead of it + itself (so it tests the combined future tree); failure removes the PR and rebuilds the ones behind; settings: build concurrency 1-100, group size 1-100 min/max with a wait timer, merge method merge/squash/rebase, "only merge non-failing PRs" (a failing PR may ride in a group if the group's last build passes, which the doc says can help with intermittent failures).
- VERIFIED (docs): Zuul dependent pipeline (zuul-ci.org gating.html, fetch): changes are tested speculatively against the assumed-successful changes ahead; on a failure ahead, the dependents are retested without it; "window" starts at 20, +1 per success, halved on failure (TCP-style); worst case degrades to one-at-a-time.
- VERIFIED (README, archived repo): bors-ng: batch of approved PRs merged onto a `staging` branch, CI runs on that merge commit, `main` is fast-forwarded to exactly the tested commit; failure bisects the batch (O(E log N)); repo archived 2024-04-04 with a pointer to GitHub's merge queue.
- VERIFIED (docs, partial): Kubernetes Tide retests PRs against the latest base before merge and runs batches; the page does not document flaky handling or batch limits (not read further).
- VERIFIED (source, gastownhall/gastown at 94cc82289d2ead275a62e1db4ef1d4ada4a1f98e, committer date 2026-11-12; repo moved from steveyegge/): the "Refinery" is two things. (a) `internal/formula/formulas/mol-refinery-patrol.formula.toml` v16, a prompt for an LLM agent ("mechanical merge processor"): per queued branch, serially: `git checkout -b temp origin/<branch>`; `git merge --no-ff --no-edit origin/<target>` (rehearsal: target merged INTO the branch tree, polecat head not rewritten); on conflict `git merge --abort` and file a conflict-resolution task, never delete the branch; else run setup/typecheck/lint/test/build on that merged tree; failures are triaged "branch regression vs pre-existing on target": regression sends FIX_NEEDED to the polecat; pre-existing files one deduplicated bug and proceeds; then `git checkout target; git merge --no-ff origin/<branch>; git push` and verifies the push by refetching. (b) `internal/refinery/engineer.go` (2,657 lines, Go): mechanical engine with a bead-based "merge slot" lock to serialize pushes to the default branch, `RetryFlakyTests` default 1, gate phases `pre-merge` (validates the SOURCE branch on target baseline: the default) and `post-squash` (validates the combined result before push, reset on failure; the source comments say it catches "broken imports, boot failures"), a pre-verified fast path (skip gates only if `origin/<target>` still equals the base the polecat verified against: "~5s merge"), and `batch.go` batch-then-bisect (MaxBatchSize default 5, BatchWaitTime 30 s, RetryBatchOnFlaky true so an innocent MR is not blamed for a flaky test). The in-repo summary "serialized merge queue" is CONFIRMED; its other characterization ("aggressive watchdog killed live working agents") is outside this lane and not checked.

## Checkpoint 5 (real clock ~13:35): worktree/harness docs + host capability probe

- VERIFIED (official doc, https://code.claude.com/docs/en/worktrees, fetched in full): Claude Code's own worktree feature: `claude --worktree <name>` creates `.claude/worktrees/<name>` on branch `worktree-<name>`, default base = repo default branch on the remote (`worktree.baseRef` "fresh"; "head" optional) with a 24 h-stale fetch capped at 5 s; `.worktreeinclude` copies gitignored files (.env); on exit it checks changed/untracked files, submodule work and NEW COMMITS and prompts instead of deleting when work exists; while an agent runs it holds `git worktree lock` on the worktree so sweeps and `git worktree remove` refuse; a periodic sweep (`cleanupPeriodDays`) removes only subagent/background worktrees older than the window AND with no changed/untracked files AND no unpushed commits, and leaves worktrees it did not create (it writes a marker into git metadata). On Windows removal deletes only the junction/symlink inside a worktree, not its target. It blocks edits/commands that resolve into the main checkout (four checks) but states these do not track `cp` or shell redirects, so it is a guardrail, not a sandbox. Subagent worktrees are removed automatically if unchanged. Background sessions (`--bg`) isolate themselves into a worktree under `.claude/worktrees/` before editing unless `worktree.bgIsolation: "none"` (agent-view doc, fetched). There is "no built-in merge flow": background sessions commit, push the branch, may open a draft PR, and "never" push to main or merge. => For Claude agents, Agent HQ's own `createWorktree` duplicates what the harness already does and is weaker at exactly the points above (no lock, no commit check, no marker).
