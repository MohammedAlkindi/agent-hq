## Claude Code hooks reference

- Source: https://code.claude.com/docs/en/hooks.md , fetched 2026-11-23 (293,716 bytes saved to the session scratchpad).
- Events listed (33): SessionStart, Setup, InstructionsLoaded, UserPromptSubmit, UserPromptExpansion, MessageDisplay, PreToolUse, PermissionRequest, PostToolUse, PostToolUseFailure, PostToolBatch, PermissionDenied, Notification, SubagentStart, SubagentStop, TaskCreated, TaskCompleted, Stop, StopFailure, TeammateIdle, ConfigChange, CwdChanged, DirectoryAdded, FileChanged, WorktreeCreate, WorktreeRemove, PreCompact, PostCompact, PreModelSwitch, PostModelSwitch, SessionEnd, Elicitation, ElicitationResult.
- HTTP hooks exist: a hook of `type: "http"` makes Claude Code POST the same JSON input a command hook would receive to a URL (optional headers with `$VAR` interpolation limited to `allowedEnvVars`, `timeout`, `onFailure: "continue" | "block"`). A 2xx JSON body is parsed with the command-hook output schema (so a hook can answer allow/deny); non-2xx, connection failure and timeout are non-blocking errors unless `onFailure` is `"block"`.
- Notification hook: matcher `permission_prompt` fires when a tool-approval prompt has waited about six seconds; `idle_prompt` fires about 60 seconds after Claude finished and the user has not typed; also `auth_success`, `elicitation_dialog`. Input carries `message`, `title`, `notification_type`, plus common fields (`session_id`, `transcript_path`, `cwd`, `hook_event_name`). The hook cannot block the notification, and it fires even when desktop notifications are turned off.
- Why it matters: this is the missing state in Agent HQ's transcript inference. D4 and the state machine in adapters/claude.js cannot tell "waiting for tool approval" from "long-running tool" from "asked a question"; `Notification/permission_prompt`, `PermissionRequest`, `Stop`, `StopFailure` and `PostToolUseFailure` can, with push latency instead of a 600 ms to 4 s watch/poll chain. Agent HQ already listens on 127.0.0.1:7787, so an HTTP hook needs no helper script. Caveats: hooks are configured in settings files the user owns (this run did not and will not change them); the six-second delay on `permission_prompt` bounds detection latency; Codex and Antigravity expose different surfaces (lane L4).
- Cross-check on this machine: ~/.claude/settings.json already registers PreToolUse guards (danger-guard, commit-guard, autonomy-guard, scrub-guard, oss-ledger-guard on Bash|PowerShell|Write|Edit|NotebookEdit|mcp__github__.*), SessionStart, UserPromptSubmit, Stop and SessionEnd hooks, so hooks do run in the developer's sessions, and a PreToolUse hook on Write|Edit already exists as a lease enforcement point (Agent HQ's `/api/leases/acquire` could be called from it).

## HTTP hook delivery test on this machine (parent run, 2026-11-24 00:5x)

- Script: `bench/hook-http-test.js` (registers `type: "http"` hooks for nine events in a throwaway settings file passed with `--settings` and `--setting-sources ""`, so the user's own settings and hooks were not used or changed; a local server on 127.0.0.1:7841 records each POST).
- Result (VERIFIED): Claude Code 2.1.331 on Windows 11 delivered `UserPromptSubmit` (about 3.6 to 5.2 s after launch, which is process start-up) and `SessionEnd` (0.2 to 0.5 s later) as `Content-Type: application/json` POSTs. Payload keys: UserPromptSubmit = cwd, hook_event_name, permission_mode, prompt, prompt_id, session_id, transcript_path; SessionEnd = cwd, hook_event_name, prompt_id, reason, session_id, transcript_path.
- Not tested: `PreToolUse`, `PostToolUse`, `PermissionRequest`, `Notification` and `Stop`, because the headless call could not reach the model (below). The premise that a local HTTP endpoint can receive Claude Code hook events on this Windows install is verified; payload fidelity for the tool and permission events rests on the docs and on lane L4/L5 source reading until experiment E5 runs.
- Side finding (VERIFIED today, plain call with no custom flags): `claude -p "Reply with the single word ok." --model haiku --output-format json` returned `result: "Not logged in · Please run /login"`, `total_cost_usd: 0`, `usage` all zeros, `stop_reason: "stop_sequence"`, `duration_api_ms: 0`. This is exactly the zero-token, zero-cost, `stop_sequence` signature of the 209 failed drafts in `.state/dispatcher/audit.jsonl` (lane L7). HYPOTHESIS, now with a matching reproduction: the dispatcher's 88% failure rate is headless-CLI authentication failure (the auth state flips; lane L7 saw one successful call at 18:49 on 11-23). The dispatcher cannot tell, because it stores only the first 300 characters of the CLI output, which end before the `result` field. Fix: store the full `result` and `is_error`, and surface "dispatcher offline: not logged in".
