## Part A: verification of prior in-repo claims

### (b) AgenticFlict arXiv:2604.03551 "84% of cross-agent conflicts in core source logic": UNSUPPORTED, and mis-described
- The arXiv id exists. Title: "AgenticFlict: A Large-Scale Dataset of Merge Conflicts in AI Coding Agent Pull Requests on GitHub", Daniel Ogenrwot and John Businge, v1 2026-04-04, AIware '26 (Montreal, July 2026). https://arxiv.org/abs/2604.03551 . I downloaded the PDF and read the full text. VERIFIED.
- What it measured: 142,652 agent-authored PRs (AIDev dataset; Codex, Copilot, Devin, Cursor, Claude Code) from 59,412 repos; 107,026 had usable commit refs; 75.03% simulated successfully (merge simulation of PR head against the base reconstructed at PR close time); 29,609 of those conflicted = 27.67% conflict rate; mean 4.36 conflicting files, median 2, mean 11.36 conflict regions, mean 540 conflicting lines per conflicting PR; per-agent rates Copilot 15.43%, Cursor 20.06%, Devin 23.04%, Claude Code 26.86%, OpenAI Codex 32.31%; conflict rate rises with PR size (about 9.9% at median churn 2 lines, about 30% at 25 lines, plateau 32-33% for 46-185 lines).
- What it did NOT measure: it measures a single agent's PR conflicting with the repository's base branch (human and any other concurrent work). It is not a study of two agents conflicting with each other. The paper text contains no "84%", no "core source logic" vs config breakdown (I grepped the full extracted text for 84, core, config, source, cross-agent, multi-agent: only unrelated hits). The paper itself calls its analysis "preliminary exploratory" and says it ignores semantic conflicts. Conflict-type labels (modify/delete, both-modified) exist in the schema but no distribution is reported in the paper body.
- Verdict on the attribution: the "84% ... in core source logic" statement is NOT in AgenticFlict (arXiv:2604.03551). REFUTED as attributed to that id.
- Real origin found (VERIFIED, PDF read): "AI Agent Pull Requests on GitHub: Frequency, Structure, and Merge Conflict Rates", George Xu, Arjun Subramanian, Nithilan Karthik (Harvard Medical School/MGH, MIT CSAIL, DevRev AI), arXiv:2607.04697 (stamped v2, 7 Jul 2026). It uses the AIDev-pop subset (33,596 agent PRs, 2,807 repos, Dec 2024 to Jul 2025). Findings: 40.2% of repos contain agent PRs open at the same time (exact overlap), but only 0.5% of co-active PR pairs (2,896 of 580,913) were cross-agent (different agent products), in 122 of 2,807 repos (about 4.3%); replaying real three-way merges on 747 sampled pairs (716 evaluable): textual conflict 41.7% for cross-agent pairs (48/115, 95% CI 33.1 to 50.9) vs 19.8% for same-agent pairs (119/601, CI 16.8 to 23.2). Conflict anatomy (Table 2, pooled over all 167 conflicting pairs, 1,646 conflicted files, NOT cross-agent only): 84.4% of conflicted FILES are source-code files, 5.1% assets, 4.0% config and CI, 3.9% manifests and lockfiles, 2.6% docs; by conflict type 57.6% content, 26.8% modify/delete, 15.1% add/add (so about 42% structural). So the in-repo "84%" is a real number but (1) from a different paper than cited, (2) it is the share of conflicted files that are source files by path class, not "core source logic" and not cross-agent-only, and (3) the cross-agent subsample is small (115 evaluable pairs), descriptive and uncontrolled (the authors say not to read it as causal), and it counts textual conflicts only. Classification: MISATTRIBUTED and OVERSTATED, partly supported by 2607.04697.
- The real, usable numbers are 27.67% of single agent PRs conflict with their base (AgenticFlict, rising with PR size) and about 2x higher conflict between PRs from different agent products (Xu et al.).

### (d) "How Do Coding Agents Spend Your Money? (2026)": real paper, title slightly off; claims partly supported
- Real title: "How Do AI Agents Spend Your Money? Analyzing and Predicting Token Consumption in Agentic Coding Tasks", Longju Bai, ... Jiaxin Pei (UMich, UT Austin, Stanford, All Hands AI, DeepMind), arXiv:2604.22750, v1 2026-04-24, v3 2026-10-02. Read PDF. VERIFIED.
- Setup: 8 frontier models, OpenHands scaffold (single agent), SWE-bench Verified (500 tasks), 4 runs per task per model.
- CONFIRMED: accuracy often peaks at intermediate cost and saturates at higher cost; same-task runs differ in cost (most expensive run about 2x the cheapest per model on average; abstract says up to 30x in the worst case); models fail to predict their own token use (correlation up to 0.39, systematic underestimate); high-cost runs show repeated file views/edits (around 50% of file actions repeated for higher-cost models).
- UNSUPPORTED as stated: "75 to 85% of spend is input tokens". The paper reports an input/output token ratio of about 154:1 for agentic coding (so about 99% of tokens are input) and that cache-read tokens dominate both token volume and dollar cost in every phase. No 75-85% figure appears in the text. Also "recursive compilation or grep loops" is not in the paper; the observed behaviour is repeated viewing/editing of the same file. "Exponential token burn" is also the in-repo writer's gloss.
- Scope caveat: single agent on SWE-bench Verified, not a multi-agent or fleet study. It says nothing about parallel orchestration.

## Part B: scaling and cooperation evidence

- Google Research/DeepMind/MIT "Towards a Science of Scaling Agent Systems" (Kim et al., arXiv:2512.08296, v1 2025-12-09, v3 2026-04-08) EXISTS. 260 configurations, 6 benchmarks (BrowseComp-Plus, Finance-Agent, PlanCraft, Workbench, SWE-bench Verified, Terminal-Bench), 5 architectures (single, independent, centralized, decentralized, hybrid), 3 LLM families. Relative change vs single agent: +80.8% (finance, centralized) to -70.0% (PlanCraft sequential planning, independent); SWE-bench Verified: all multi-agent variants slightly worse than single agent (-2% to -15%), on a 20-instance subset; Terminal-Bench mixed (+2% independent, -19% centralized). Capability ceiling: when single-agent baseline exceeds about 45%, adding agents gives negative returns (beta=-0.236). Error amplification: independent agents 17.2x, centralized 4.4x. R^2=0.373 cross-validated (so a weak predictive model). VERIFIED (read PDF).
- CooperBench (Khatua et al., Stanford + SAP, arXiv:2601.13295, v1 2026-01-19): 600+ tasks, 12 libraries, 4 languages; two agents each implement a feature that is compatible but potentially conflicting. Coop success about 30% lower on average than Solo (one agent doing both features); for GPT-5 and Claude Sonnet 4.5 Coop about 25% vs solo about 2x. Scaling agents on 46 tasks: 68.6% (2 agents), 46.5% (3), 30.0% (4). Communication tool: no significant gain in success but cuts merge conflicts; first-turn plan message halves conflict rate (29.4% vs 51.5%). Failure symptoms (LLM-judged, failed Coop traces): work overlap 33.2%, divergent architecture 29.7%, repetition 14.7%, unresponsiveness 8.7%. VERIFIED (read PDF).

## Part C: production-system claims (raw page text read unless marked)

### (c) "Cursor: lock contention made 20 agents act like 2 to 3": CONFIRMED, but narrower than the in-repo wording
- Source: Cursor blog "Scaling long-running autonomous coding" (Wilson Lin), 2026-01-14, https://cursor.com/blog/scaling-agents . I fetched the raw HTML and read the sentence myself: with a shared coordination file plus a lock used so two agents would not claim the same task, 20 agents slowed to the effective throughput of 2 or 3, most time spent waiting; agents also held locks too long, forgot to release, or updated the file without the lock. VERIFIED (raw page text).
- Scope: it is a task-CLAIMING lock on a shared status file in a flat swarm, not git or per-file leases. It is one anecdotal sentence, self-reported, no measurement method, no throughput numbers. They then tried optimistic concurrency (read freely, write fails if state changed): simpler, more robust, but agents became risk-averse (small safe edits, nobody owns hard work). They moved to planner / worker / judge roles. The follow-up post "Self-driving codebases" (2026-02-05, https://cursor.com/blog/self-driving-codebases, read via fetch tool summary) says the final design gives each worker its own repo copy, workers do not talk to each other, planners own delegated slices, overlapping edits are tolerated and allowed to converge; demanding 100% correct commits caused serialization; an integrator role was removed as a bottleneck; peak about 1,000 commits/hour on git.

### Cursor "agent swarm model economics" (2026-07-20, https://cursor.com/blog/agent-swarm-model-economics): strongest production-grade quantitative evidence on contention (raw page text read)
- Task: swarms build SQLite in Rust from the 835-page manual, graded on sqllogictest, 4-hour budget. Old harness vs new harness, same models.
- Old harness: more than 70,000 merge conflicts before being paused (Grok 4.5 run paused before 2 hours); hottest file had 7,771 conflicts touched by 1,173 different agents; sprawled to 54 crates; about 68,000 commits in 2 hours (about 70x the new run's pace, which the authors read as busywork not productivity).
- New harness: under 1,000 conflicts in 4 hours; most contested file had 47; 9 crates. New-harness runs scored 73-85% at 4 hours vs 11-77% old; every new configuration eventually reached 100%.
- Costs: $1,339 (Opus 4.8 planner + Composer 2.5 workers) to $10,565 (GPT-5.5 alone); workers consume at least 69% of tokens (over 90% in most runs); planner tokens are few but costly (about two-thirds of cost in the Opus hybrid).
- Caveats (the post states them): only 4 configurations, apparently single runs per configuration, vendor-produced, solo Opus/Fable runs graded only informally.
- Mechanisms they credit: a design doc, a neutral third-party agent that resolves merge conflicts for all parties, decomposing "megafiles", "licensed breakage" (tolerating temporary breakage), stacked reviewers, a shared Field Guide.

## Part D: parallel-coding papers (PDF text read by me unless noted)

- ParallACT / "Decentralized Multi-Agent Coordination and Communication in Shared Codebases" (Mediratta, Xiao, Stone, Biswas, Stengel-Eskin; UT Austin + NVIDIA; arXiv:2611.00314, v1 2026-10-30). Setting is exactly Agent HQ's: independent requests from one developer to agents in a shared repo (no orchestrator). 155 instances (85 for the Claude Code + Opus 4.8 arm), complementary vs contradictory task pairs, single-agent oracle (one agent given both tasks). Opus 4.8 in Claude Code: contradictory 62% oracle -> 16% parallel-unaware; complementary 86% -> 57%. Six open-weight configs: 60% -> 19% and 72% -> 53%. Peer awareness (telling an agent a peer exists): 16% -> 26%, not significant. Messaging/sync channels: 20-22% (file sync) up to 32% (Redis sync) at 1.4-2.2x the oracle's token cost; communication oracle 56-58%. One sequential hand-off (B starts after A and sees A's code) 16% -> 54% at the same token cost (1.18x oracle). Re-entrant ABAB gave no gain at 1.88x cost. Post-hoc reconciliation (concatenate 10%, git merge 14%, LLM reconciler 16%) recovers little. Gold tests alone did not close the gap (98% oracle vs 38% parallel). VERIFIED.
- Passes Alone, Fails Together (Xia, Wu, Park; UIUC/Columbia; EXPRESS '26 workshop, arXiv:2609.25396, 2026-09-21). Real mined Django PR pairs (417 pairs, 834 runs, GPT-5-class agent in mini-swe-agent): only 1 run showed semantic interference once grading was corrected, i.e. independent reviewed PRs rarely interfere. Constructed tasks on 12 real Django helpers (GPT-5.5): interference in 105/108 runs (97%); a message describing the completed concurrent change recovered 89/108 (82%). The authors say the constructed rate does not estimate real-world frequency. VERIFIED.
- Claim Plane (Nikolaev, Vladivostok State University; arXiv:2607.21909 design paper 2026-07-24, arXiv:2608.00947 confirmatory study 2026-08-02; single-author preprints, code github.com/SkeinRank/claim-plane, data on HF). 30 frozen CooperBench pairs (15 conflict, 15 clean), 3 coder seeds, 360 executions, DeepSeek V4 Flash coder, planner declarations frozen. Static pre-write admission (declare scope before editing, serialize overlaps): pair pass 23.3% -> 50.0% (paired +26.7 pp, 95% CI 9.6 to 60.0), integration success 65.6% -> 96.7%, BUT it serialized 96.7% of executions (93.3% of clean pairs), i.e. reliability came largely from collapsing to serial; provider calls were physically sequential so no wall-clock speedup was measured. Dynamic admission (serialize only overlaps): serialized 66.7% of conflict and 13.3% of clean pairs but 46/90 executions failed closed on undeclared scope, pair pass only 22.2%; 45 of 46 blocks hit files already in the declarations (region undercoverage). VERIFIED (abstract + intro read; not every table).
- NP-Bench / Nerveplane (Muku, Amira Learning; arXiv:2610.07261, 2026-10-05; single author). Deterministic 9 scenarios: clean integration 1/9 (no coordination) -> 4/9 (reactive detection) -> 9/9 (up-front scope partition + merge order); conflicts 13 -> 0. Live agents on a breaking contract change: no coordination 0.00, reactive "someone may be touching X" warning 0.00 on every model (the agent knew something might change and still coded to the stale field), proactive plan 1.00 (Opus 4.8, K=15) / 0.60 (Haiku 4.5) / also tested GPT-5-Codex. Scopes were hand-seeded, not inferred (the authors state scope inference is unbuilt). A decision recorded in one session cut repeated-mistake rate 1.00 -> 0.00 (synthetic). Small K (3-15 seeds), hand-built scenarios. VERIFIED (read key sections).
- MemMux (Muku; arXiv:2610.07257, 2026-10-05, v2 2026-10-21): runtime for fleets of parallel coding agents on one workstation: per-agent memory attribution via PSS, subtree reclamation, escaped-child detection (10/10 injected escapes), admission control under a memory budget. Linux hosts mainly (macOS cross-check; no Windows result); under a binding 7,500 MiB budget raw and tmux overcommit about 2x and spill about 2 GiB to swap, MemMux holds the budget with zero swap; always-on 1 Hz monitor costs 0.6% CPU at 1 agent to 2.7% at 10 (above its own 2% target). Mostly synthetic workloads; also real Claude Code sessions for attribution. VERIFIED (abstract + sections skimmed).
- "Failure as a Process: An Anatomy of CLI Coding Agent Trajectories" (Zhao, Li, ... Barr, Sarro, Ye; UCL; arXiv:2607.09510, 2026-07-10). 3,843 Terminal-Bench trajectories from 7 frontier models x 3 scaffolds (OpenHands, MiniSWE, Terminus2); 1,794 manually annotated (63,000+ steps); 1,184 failed. Median decisive error at step 7, unrecoverable (lock-in) about step 12, first externally observable failure signal about step 16. A prefix monitor (independent Sonnet 4.6) flagged only 3.7 to 8.7% of failures at or before lock-in, with 2 to 3% false positives on successful runs. Root causes: epistemic 57.9% (false premise 30.7% largest), competence and environment the remainder. After lock-in only 18% of failed runs stop quickly; 24% keep repairing the wrong problem (39% of all wasted steps, median 21 more steps), 15% repeat the same approach (29% of waste), 28% run checks that cannot change the outcome, 15% claim success with fabricated evidence. 71% of successful runs also hit at least one error; successful recoveries are short (median 5 steps vs 12 for failed). VERIFIED (read PDF).
- Cohere "Scaling Inference-Time Compute with Teams of Coding Agents" (Samway, D'souza, ... Dziri; arXiv:2610.17471, 2026-10-12): teams beat solo on long-horizon SWE tasks (ProgramBench) but cost 3 to 7x; delegating only planning to workers matched full delegation at half the cost; cheap models as planners recover 47.5% of the gain for 13.9% of the added cost, cheap implementers lower reward; planners keep helping with more workers while implementers and verifiers plateau beyond about 4 workers (extra implementers fragment code into more files). VERIFIED (abstract); body not read.
- MSEval/LegoGent (Ren et al., Tsinghua; arXiv:2607.27877, 2026-07-30): 10 from-scratch full-stack projects x 10 collaboration topologies, 100 runs; for identical tasks and models, topology alone moved scores by more than 30 points and doubled wall-clock time; structured pipelines converged fastest with best quality; heavy manager (PM) oversight degraded results. From-scratch web projects, university-course-derived rubrics, so weak transfer to brownfield editing. VERIFIED (abstract).
- When Parallelism Pays Off: Co-Coder (Yang, Nie, ... Chaudhuri; UT Austin + Oxford; arXiv:2606.00953, 2026-05-31): dependency graph from static analysis, isolate hub files, Infomap community detection, dependency-aware list scheduler. 28 Python repo-generation tasks (DevEval, CodeProjectEval), all arms use gpt-5-mini. DevEval: Co-Coder 68.1% vs sequential 56.8% pass, 442 s vs 800 s, $0.18 vs $0.25; naive file-based parallel 57.7% pass, no latency gain (806 vs 800 s), +44% cost; Claude Code Agent Teams (v2.1.119 via LiteLLM proxy with gpt-5-mini) 54.1% pass, 536 s. CodeProjectEval: Co-Coder 34.1% vs sequential 20.1%, 1315 s vs 2756 s, $0.67 vs $1.03; file-parallel 23.3% at +60% cost; Agent Teams 16.3% pass (below sequential), 680 s, $0.38. Limits: Python only, generation from specs not editing, near-fully-coupled repos collapse to one partition = sequential. VERIFIED (read results).
- AgentRoom (Cho, Lee; arXiv:2608.23740, v2 2026-11-12): CRDT-merged shared filesystem + MCP claim/release/status/broadcast tools. At 2 agents it lowers the rate of lone-agent "stub-and-exit" abandonment (a run scoring below 0.3 that exits within 200 s or leaves at most two source files). Small n per cell (n=6 to 35), from-scratch tasks, authors' own judge rubric; the sequential ChatDev-style pipeline scored lowest (0.333) and parallel-merge 0.456 vs solo 0.544 vs AgentRoom 0.669 (matched compute, n=14). Claims "coordination, not parallelism or CRDT-merge" is the key. VERIFIED (abstract + results lines); weak evidence (small n, same-author scorer).
- CoAgent (Lyu, ... Chen; SJTU; arXiv:2606.15376, 2026-06-13): classic concurrency control for LLM agents sharing a mutable environment (K8s, bash, git tree). Locks block minutes-long inference; OCC abort-and-retry discards minutes of work. 2PL gets 1.04x speedup and OCC 0.93x (slower than serial); their "notify the agent, let it re-judge and repair, with saga-style undo" gets 1.4x speedup at within 5% of serial correctness and 1.15x token cost on 10 contended workloads. Workloads are tool-state mutation (K8s etc.), not source code editing. VERIFIED (abstract + intro).
- AsynCodeBench (Zhang et al.; arXiv:2609.32662, 2026-09-26): 19 tasks, 52 cross-agent dependencies; coding ability does not imply collaboration ability; task-level metrics diverge from dependency-level metrics; dependencies resolve in "hopping windows" (bursts). Abstract only.

## Part E: supervisor, loop-detection, harness evidence (and later additions)

- SHEPHERD (Yu, Chong, ... Manning, Shi; Northeastern + Stanford; arXiv:2605.10913, v1 2026-05-11, v3 2026-06-24). The most direct evidence for "an external supervisor over parallel coding agents helps". Two Claude Haiku 4.5 workers each implement one CooperBench feature in isolated sandboxes; a meta-agent (Sonnet 4.6 or Opus 4.7) subscribes to both workers' tool-call event streams and every 5 s makes one batched decision per agent from {none, steer/inject, redirect/handoff, revert/discard}. Pair pass rate on all 479 CooperBench pairs: coop baseline 28.8%, Sonnet supervisor 45.3%, Opus supervisor 54.7%, solo ceiling 57.2%. Wall-clock per pair: coop 19.8 min, Sonnet 21.2 (1.4 min supervisor overhead), Opus 24.2 (4.3 min), solo 28.4. Supervisor snapshot per tick = feature text (350 chars), event count, consecutive-error count, modified-file set, last intervention and when, trailing 25 tool-call summaries (about 150 bytes each); the per-tick prompt stays under 3K tokens even with 10 agents, so supervisor token cost is flat in worker count. The prompt's heuristics: default to "none", "loop" means 10+ identical tool calls with no progress (3-5 retries is normal), prefer steer over redirect over revert, do not re-intervene within a tick or two, different agents editing the same file is usually fine unless the same lines with different intent. Authors call it proof of existence; supervisor token cost can exceed worker cost on short tasks; single benchmark, weak workers, no seeds reported in what I read. VERIFIED (read section 5.1, appendix E prompt and A.1 limitations).
- Wink: Recovering from Misbehaviors in Coding Agents (Meta; Nanda, Maddila, ... Chandra; arXiv:2602.17037, 2026-02-19). Production taxonomy from real traffic: specification drift, reasoning problems (incl. repetitive loops), tool call failures; one or more present in about 29.2% of trajectories (12,499 flagged). An asynchronous observer LLM runs every k=5 steps and injects a short course-correction into the agent's context; on 10,000+ real trajectories it resolved 90.93% of misbehaviors needing one intervention (79.07% if the agent needed several); live A/B on production traffic: tool-call failure rate 5.29% -> 5.07% (-4.2%), tokens per session -5.3%, engineer interventions per session -4.2% (all statistically significant), session execution time -4.3% (not significant at the stated level). Effects are modest at the fleet level. The VS Code assistant platform, not CLI sessions. VERIFIED (read abstract, results, table 5).
- OpenHands software-agent-sdk StuckDetector (file openhands-sdk/openhands/sdk/conversation/stuck_detector.py, repo OpenHands/software-agent-sdk, commit 0988e976491ff733bc09e976b36a271b0c511530, read 2026-11-23; thresholds in openhands-sdk/openhands/sdk/conversation/types.py class StuckDetectionThresholds). Four rule-based patterns over the last 20 events since the last user message: identical action+observation repeated 4 times; same failing action with the same error 3 times (and a one-shot textual nudge when the streak first hits the threshold); 3 consecutive agent messages with no tool call (monologue); alternating A,B,A,B pattern over 6 pairs. Pure equality tests, no LLM. VERIFIED (source read).
- Agent HQ comparison (code read, adapters/claude.js lines 712-718): the existing "stuck" flag is only "state is working, last event is a tool call, no new event for more than 8 minutes". It has no repetition, same-error, monologue or alternating-pattern detection, no premature-completion check, and no compaction/context-loss signal.
