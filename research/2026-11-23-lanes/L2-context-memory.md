## Checkpoint 2 (13:15 wall clock): primary sources read so far

### S1. CodeNib paper (the "50 to 87% / outperforms on-demand exploration" claim)
- Title: "CodeNib: A Multi-View Data System for Serving Repository Context to Coding Agents". Zhongming Yu, Hengjia Yu, Boqin Yuan et al. arXiv 2607.25431, v1 2026-07-28, v2 2026-09-28, cs.SE. URL https://arxiv.org/abs/2607.25431 . I downloaded the v2 PDF and read it via pdftotext (sections 7.4, 9.7, 9.9, 10.1). Authors are the repo owners (sysevol-ai/CodeNib, Apache-2.0, 112 stars, created 2025-03-09, last push 2026-11-23, head commit 57a2cf3 "feat(walkthrough) ... (#1138)"). Self-published preprint; the README badge claims a Hugging Face "Paper of the Day". I found no independent replication.
- Mechanism: indexes a repo at one commit into lexical (BM25), dense (embedding) and structural (SCIP symbol graph) views behind one manifest; serves "bounded candidate packs" over MCP; in the "compact" policy the harness injects top-10 candidates into the task message and, after the agent's first source read, rewrites history to drop the delivered block ("retire").
- Evidence, what each number actually is (all VERIFIED from the PDF text):
  - "50 to 87% fewer tokens" = Q5 context-delivery study in the authors' own harness (16-turn cap, frozen top-10 candidates, localization task scored by AnswerRecall@5), five models. For each model, the lowest-token arm that meets a margin (epsilon = 0.05 on a paired 95% lower bound, "not a pre-registered equivalence test") used 49.9, 45.1, 44.8, 12.9 and 35.8% of paired grep/read tokens, i.e. 50 to 87% fewer. It is a localization result, not patch correctness; the authors say it does not extend to learned exploration or patch correctness. Same section: Compact vs Eager token use ranges from 123.3% (Haiku) to 27.9% (Gemma); "compaction is not uniformly dominant".
  - "outperforms on-demand exploration" = Q7: 200 SWE-bench Verified tasks, ONE model (Claude Haiku 4.5, smallest tier), mini-SWE-agent, USD 1 stop rule, 100 steps, ONE run per task per policy (two extra runs on only 10 tasks). Resolved: CodeNib compact 79, on-demand 66, CodeNib eager 69, BM25 eager 63, Aider repo map 56. Discordant pairs 22 vs 9, exact McNemar p = 0.0294 (predeclared; worst-case fill p = 0.0502). Difference +6.53 points, task-paired CI [+1.01, +12.06]. Clustering by repository (92 of the 200 tasks are Django) widens the CI to [-3.92, +17.42]; sympy runs against it; gain is concentrated in Django and xarray; with a USD 2 budget on the 108 non-Django tasks the gap shrinks to 50 vs 46 (+3.7 points, CI [-3.7, +11.2]); repeated runs flip outcomes on 2 of 10 (compact) and 4 of 10 (on-demand) tasks. Mechanism per the authors: compact submits more often (98 vs 81 of 200) while accuracy per submission is identical (0.81 each), i.e. a budget effect. Compact vs eager (the retention effect itself) is +4.0 to +5.5 points with a Holm-adjusted test above 0.05, i.e. not significant.
  - Q6: behind LocAgent (an agent they did not write) substituting CodeNib views, 78 of 90 cells complete vs 65 native, -43.5k tokens, -18.6 s; 30 tasks only; mechanism is shorter tool replies (3,681 vs 6,375 chars median).
- Verdict on the in-repo claim: it is a compressed, over-general paraphrase of the abstract. The abstract does say both things. MISLEADING because the 50-87% is localization-only against grep/read in a custom capped harness; "outperforms" holds under a binding USD 1 budget, one cheap model, one run, with a repo-clustered CI that includes zero. It is a vendor-authored result and supports "less context per turn buys more turns under a fixed budget", not "a code index beats exploration for a Sonnet/Opus-class agent with a 1M window".
- Applicability to Agent HQ: none directly (it is an MCP server the harness calls). Indirect: retire-after-first-read is observation masking, same family as S2. Agent HQ cannot do that from outside (no hook into model requests). Effort L; no recommendation.

### S2. "The Complexity Trap: Simple Observation Masking Is as Efficient as LLM Summarization for Agent Context Management"
- Tobias Lindenbauer, Igor Slinko, Ludwig Felder, Egor Bogomolov, Yaroslav Zharov (JetBrains Research). arXiv 2508.21433, v1 2025-08-29, v3 2025-10-27, cs.SE. https://arxiv.org/abs/2508.21433 . PDF downloaded; I read Table 1 and sections 4.4 and 5.3.
- Mechanism: SWE-agent on SWE-bench Verified (500 instances), 250-turn limit. Raw agent vs Observation Masking (keep the last M=10 turns' observations verbatim, replace older observation bodies with a placeholder, keep reasoning and actions) vs LLM-Summary (every N=21 turns summarize with an LLM, keep last M=10) vs Hybrid (masking until N=43 turns, then summary).
- Evidence (VERIFIED, Table 1, 95% bootstrap CIs, ONE run per configuration): cost per instance down about 50% for most models; e.g. Qwen3-Coder 480B raw 53.4% solve at $1.29, masking 54.8% at $0.61, summary 53.8% at $0.64; Gemini 2.5 Flash 32.8/35.6/36.0 solve at $0.41/$0.18/$0.24. Counter-case: Gemini 2.5 Flash (thinking) solve 40.4 raw vs 36.4 masking vs 31.4 summary (masking -4.0 pp, summary -9.0 pp). Qwen3-32B (thinking) cost saving is small (median trajectory about 15 turns). LLM-Summary "trajectory elongation": Gemini mean 52 turns vs 44 masking vs 50 raw; Qwen3-Coder +15% vs raw. Summarizer calls are 0.65 to 7.2% of cost and miss the cache. Hybrid (Qwen3-Coder, 50-instance subset only): +2.6 pp solve, 7% cheaper than masking, 11% cheaper than summary. OpenHands check = 50-instance slice, one model, window retuned (M=58). Limits stated by the authors: SE-only (verbose observations), fixed triggers, one run per cell.
- Applicability to Agent HQ: tells us what NOT to build (a summarizer to "compact" other tools' sessions). Agent HQ cannot mask observations inside Claude Code/Codex; those harnesses own that. Supports a gauge plus a nudge to start a fresh session at task boundaries rather than an LLM summarizer. Effort S for the gauge; no build for compaction.

### S3. "Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?"
- Thibaud Gloaguen, Niels Mündler-Sasahara, Mark Niklas Müller, Veselin Raychev, Martin Vechev (ETH Zurich, LogicStar.ai). arXiv 2602.11988, v1 2026-02-12, v3 2026-09-29, cs.SE; no venue listed. PDF read for results.
- Mechanism: new benchmark CTXBENCH (138 instances, 12 niche Python repos that have developer-committed context files) plus SWE-bench. Each task run with (a) no context file, (b) an agent-generated context file (each agent's own /init-style recommended prompt), (c) the repo's developer-written file. Agents: Claude Code (Sonnet 4.5), Codex (GPT-5.2, GPT-5.1 mini), Qwen Code (Qwen3-30B-Coder).
- Evidence (VERIFIED): LLM-generated files changed resolution rate by -0.5 pp (SWE-bench, CMH p=0.87) and -2 pp (CTXBENCH, p=0.37), i.e. no significant effect, but raised cost 20% and 23% (p<0.001) and steps +2.45/+3.92. Developer-written files: +2.4 pp on average (p=0.21, not significant), up to +19% cost; developer-written beat LLM-generated (p=0.038). "Repository overview" sections did not reduce steps-to-first-relevant-file; 100% of Sonnet-4.5-generated files contained overviews. Instructions are followed (tools named in the file are used about 1.6x to 2.5x more). When all documentation is deleted from the repo, LLM-generated files help (+2.7 pp on average), so generated files are mostly redundant with existing docs. File length did not predict outcomes.
- Applicability to Agent HQ: directly relevant to `knowledge.js` and to any plan to auto-write gotchas/decisions/graph and inject them. Evidence says auto-generated context is neutral on success and about +20% on cost; only short, human-curated "non-standard practice" instructions have any positive signal (and even that was not significant). Do not auto-inject.

### S9. Claude Code context facts (official docs, read)
- Statusline JSON (https://code.claude.com/docs/en/statusline): `context_window.used_percentage` = (input_tokens + cache_creation_input_tokens + cache_read_input_tokens) / context_window_size, from the LAST API response; output tokens excluded; `context_window.current_usage` null or zeros right after /compact; `exceeds_200k_tokens` is a fixed 200k threshold that includes output tokens. When CLAUDE_CODE_AUTO_COMPACT_WINDOW is set, the docs say used_percentage "doesn't indicate when compaction will run".
- Auto-compact (https://code.claude.com/docs/en/model-config#default-auto-compact-thresholds): default is to compact when the conversation reaches the model's context limit; models with a native 1M window (Fable, Sonnet 5 and later, Haiku 5.5, Opus 4.7 and later) compact at about 967K tokens by default; models at 200K compact at the 200K boundary; user can lower it with /autocompact, `autoCompactWindow`, `--autocompact`, or CLAUDE_CODE_AUTO_COMPACT_WINDOW (min 100k). There is also `idleCompaction`. Auto-compact stops after a few thrashing attempts and shows an error.
- What survives compaction (https://code.claude.com/docs/en/context-window#what-survives-compaction): CLAUDE.md, auto memory and the plan re-injected from disk; up to five most-recently touched files re-read (files over 5k tokens come back as path references); invoked skill bodies capped 5k each / 25k total; `SessionStart` hooks with matcher `compact` run and add output to the compacted context.
- Hooks (https://code.claude.com/docs/en/hooks, partially read): PreCompact (matchers manual/auto; exit 2 blocks compaction; stdout on exit 0 becomes instructions for the summary), PostCompact, SessionStart matcher compact, UserPromptSubmit additionalContext, Stop. Common stdin fields: session_id, transcript_path ("written asynchronously and may lag"), cwd.
- Consequence for the in-repo "red above 120k" gauge: for the 1M-window models this user runs (Sonnet 5.x, Opus 4.7+), Claude Code does not compact until about 967K, so 120k is 12% of the window, not a pressure point; for 200K-window sessions it is 60%. A fixed absolute threshold ignores the window size. The CLAUDE_CODE_AUTO_COMPACT_WINDOW override can also make used_percentage misleading.

### S12. Persistent-memory literature
- Sleep-time Compute: Kevin Lin, Charlie Snell, Yu Wang, Charles Packer, Sarah Wooders, Ion Stoica, Joseph E. Gonzalez (Letta + UC Berkeley). arXiv 2504.13171, 2025-04-17, cs.AI. PDF read for section 6. Mechanism: before the query arrives, a model re-represents a fixed context into inferences/precomputed answers (c -> c'), then test-time uses c'. Evidence: Stateful GSM-Symbolic and Stateful AIME (math problems split into context + question): about 5x less test-time compute at equal accuracy; up to +13% / +18% accuracy when scaling sleep-time compute; Multi-Query GSM-Symbolic amortization 2.5x lower cost per query; benefit correlates with how predictable the query is from the context. SWE case study ("SWE-Features", 3+ file PRs from large repos, scored by F1 of the predicted SET of modified files, not by tests): at low test-time budgets sleep-time helps (up to about 1.5x fewer test-time tokens) but at high budgets plain test-time compute is better (higher precision). The paper does NOT study deduplicating/consolidating memory or ADR/gotcha files, and it says explicitly that unpredictable queries make it less effective. The Letta product "sleep-time agent" (blog https://www.letta.com/blog/sleep-time-compute, relayed) is a second agent that edits shared memory blocks asynchronously; its product-level claims are not measured in the post.
- LongMemEval: Di Wu, Hongwei Wang, Wenhao Yu, Yuwei Zhang, Kai-Wei Chang, Dong Yu. arXiv 2410.10813, ICLR 2025. 500 questions over scalable chat histories, five abilities; commercial assistants and long-context LLMs lose about 30% accuracy over sustained interactions; indexing/retrieval/reading optimizations help. Conversational QA, not coding. Chroma (S5) used it to show focused ~300 tokens beat full ~113k tokens.
- Mem0: Chhikara et al., arXiv 2504.19413, 2025-04-28: on LoCoMo reports +26% relative LLM-judge score vs OpenAI's memory, 91% lower p95 latency and over 90% token saving vs full context. Authors are the company. Zep/Graphiti: Rasmussen et al., arXiv 2501.13956, 2025-01-20: DMR 94.8% vs MemGPT 93.4%, LongMemEval up to +18.5% accuracy and -90% latency; authors are the company. A-MEM: Xu et al., arXiv 2502.12110, NeurIPS 2025 (Zettelkasten-style linked notes; abstract gives no numbers).
- Disputes (leads, not primary): Zep's blog "Lies, Damn Lies & Statistics" says Mem0 mis-ran Zep (Zep 75.14% vs 65.99% reported by Mem0); Letta's blog https://www.letta.com/blog/benchmarking-ai-agent-memory (relayed) reports a plain filesystem agent (grep, search_files, open; GPT-4o-mini) at 74.0% on LoCoMo vs Mem0's self-reported 68.5%, and concludes that agent behavior matters more than the memory mechanism; Letta itself notes the comparison is disputed. An audit by Penfield Labs (a competing memory vendor, secondary, not verified by me) claims 6.4% of LoCoMo's answer key is wrong (99 of 1,540) and that the judge accepts up to 63% of deliberately wrong answers; DolphinBench (arXiv 2609.24971, 2026-09-21, authors include Mem0's CEO and CTO) proposes task-completion memory evaluation with cost and latency reported, abstract gives no results.
- Net: every headline memory number is from the vendor, on conversational QA (LoCoMo, LongMemEval, DMR), with disputed or noisy benchmarks; none is on coding-agent tasks; the one neutral-ish result (Letta's) says plain files with grep are competitive.

### S13. Compaction and folding research (abstract level; full texts NOT read)
- ACON (Kang et al., Microsoft; arXiv 2510.00615, ICML 2026): LLM-optimized compression guidelines for observations and history; AppWorld, OfficeBench, multi-objective QA; 26-54% lower peak tokens, task success maintained or improved over compression baselines; distillable into smaller compressors. Not coding.
- ReSum (Wu et al., Alibaba; arXiv 2509.13313, 2025-09-16): periodic summarization tool for web-search agents; +4.5% over ReAct training-free, +8.2% more with ReSum-GRPO RL. Needs RL for best result; not coding.
- Context-Folding (Sun et al., ByteDance; arXiv 2510.11967, 2025-10-13): agent branches into sub-trajectories and returns only a summary; trained with FoldGRPO; Deep Research and SWE tasks, matches or beats ReAct with 10x smaller active context. Requires RL training of the model; cannot be bolted on from outside.
- Anthropic Claude Code already ships the practical equivalent of these: subagents with own context windows (docs read), compaction, tool-result clearing in the API.

### S14. Cost and token-spend studies (primary arXiv, read)
- "How Do AI Agents Spend Your Money? Analyzing and Predicting Token Consumption in Agentic Coding Tasks", Longju Bai, Zhemin Huang, Xingyao Wang et al., arXiv 2604.22750 (v1 2026-04-24, v3 2026-10-02). This is the paper the in-repo "How Do Coding Agents Spend Your Money?" most plausibly refers to (title differs). ### S15. Code retrieval and indexing for agents
- Cursor, "Improving agent with semantic search" (https://cursor.com/blog/semsearch, relayed via summarizing fetch): offline Context Bench average +12.5% accuracy (range 6.5% to 23.5% by model) with semantic search plus grep vs grep only; online A/B: code retention +0.3% overall and +2.6% on codebases with 1,000+ files; 2.2% more dissatisfied follow-ups without it.
