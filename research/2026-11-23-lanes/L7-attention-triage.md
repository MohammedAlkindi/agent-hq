### 2.1 Anthropic Engineering, "How we built Claude Code auto mode: a safer way to skip permissions"
- URL https://www.anthropic.com/engineering/claude-code-auto-mode ; date 2026-03-25 (relayed from lane L1; the fetched text did not show it). Type: production system write-up (vendor). Read via fetch tool (paraphrase).
- Mechanism: two layers. An input-layer prompt-injection probe scans tool outputs (file reads, web fetches, shell output) before they reach the agent and adds a warning if content looks like hijacking. An output-layer transcript classifier gates each action before execution: stage 1 is a single-token yes/no filter told to err toward blocking; stage 2 runs chain-of-thought only on flagged actions and reuses stage 1's prompt (cache hits). Classifier model Sonnet 4.6. The classifier sees only user messages and the agent's tool calls, not assistant prose and not tool outputs ("reasoning-blind" by design). Allowlisted read-only tools, user allow rules and in-project file edits skip it. A denial returns to the agent as a tool result; 3 consecutive or 20 total denials stop the model and escalate to the human (headless `-p`: the process ends).
- Evidence: the sentence that users accept 93% of manual prompts anyway is the source of the 93% figure and the only place it appears (no n, no window, no population). Measured: real internal traffic n=10,000 tool calls, FPR 8.5% (stage 1) to 0.4% (full pipeline); real overeager actions n=52, FNR 6.6% to 17%; synthetic exfiltration n=1,000, FNR 1.8% to 5.7%. Anthropic calls the 17% "the honest number" and says the misses are mostly the classifier treating earlier approval-like text as consent. No latency or cost numbers.
- Applicability: (a) settles the provenance of "93%"; (b) the design is the opposite of Agent HQ's dispatcher input policy, which feeds the agent's own reply (derived from tool results) to the model; (c) two-stage cheap-then-reasoning classifier and the 3/20 circuit breaker are copyable into `dispatcher.js` (effort M); (d) the 17% FNR on n=52 is the honest ceiling for LLM gating of risky actions. Risk: the classifier sits on tool calls, not on free-text replies, so its numbers do not transfer to reply drafting.

### 2.7 Agent HQ dispatcher, policy and logs (source and data)
- `dispatcher.js` (273 lines), `dispatcher-policy.json`, `.state/dispatcher/{audit.jsonl,drafts.json}`. Type: source code and own-use data; baseline in section 0.
- Mechanism (VERIFIED by reading): `claude -p` launched with `--tools ""`, `--strict-mcp-config` with an empty MCP config, `--setting-sources ""`, `--disable-slash-commands`, `--no-session-persistence`, cwd = temp dir (L175-178), so the model has no tool, MCP or settings authority. The prompt (L123-155) puts `<policy>` (rules R1 to R3, alwaysHuman list) and `<session>` (title, folder, last user message capped at 2500 chars, agent reply capped at 6000, pending question capped at 4000) in one user message; the SYSTEM text (L115-121) says tag contents are data. Gate to wouldSend (L186-201): action answer|continue, non-empty reply, no needs_human, no regex hint (money, legal, credentials words only, L58-62), a policy rule id returned by the model that exists in policy, confidence at least 0.8, not on the hold list (title substring), fewer than 3 prior would-sends for the session this hour, reply not identical to the last reply.
- Weaknesses found: (1) `cap()` keeps the FIRST N chars, so the tail of a long agent message, where the question normally is, is cut; (2) untrusted text is inserted verbatim, a literal `</agent_reply>` or `<policy>` inside agent output is not escaped or marked; (3) the per-session rate limit counts only past would-sends, so a model that never reaches would-send is never limited, and the loop check is exact string equality, which a paraphrase defeats; (4) the regex hints are keyword lists for three classes and say nothing about destructive git, publish, install, network fetch, or secrets in diffs, which are guarded only by the LLM's `needs_human`; (5) rules R1 to R3 are generic ("safe, reversible, proceed", "do not stop to confirm when tests fail"), so "a rule clearly covers it" is itself a model judgment an attacker can steer; (6) nothing escalates when the dispatcher itself keeps failing (section 0).
- Applicability: the baseline all recommendations modify.

### 2.9 Hines et al., "Defending Against Indirect Prompt Injection Attacks With Spotlighting" (arXiv:2403.14720, v1 2024-03-20)
- Type: paper, Microsoft authors; PDF text read by me.
- Mechanism: three transformations that keep the origin of text visible to the model: delimiting (special markers around the document), datamarking (a marker token interleaved through the document), encoding (base64 or similar).
- Evidence: models GPT-3.5-Turbo, GPT-4, text-davinci-003; delimiters plus a defensive instruction reduce ASR "by about half" from roughly 60% on GPT-3.5-Turbo; datamarking cut ASR from roughly 50% to below 3% (summarisation) and to 0% on text-davinci-003 (Q&A: 8.0% GPT-3.5, 1.0% GPT-4); encoding reached 0.0% (summarisation) and 1.8% (Q&A) on GPT-3.5 but degraded task quality on GPT-3.5. The authors explicitly do not recommend delimiting alone, recommend at least datamarking, and suggest a fresh random marking token per call because the system prompt must be assumed leaked. No adaptive attacker; 2024-era models.
- Applicability: Agent HQ's tags are delimiting plus an instruction, the variant the paper discourages. Datamarking the agent reply and using a random boundary per call is an S-effort change in `buildPrompt`. The gain was measured against non-adaptive attacks, so treat it as a speed bump, not a boundary (2.10, F9).

### 2.10 Beurer-Kellner et al., "Design Patterns for Securing LLM Agents against Prompt Injections" (arXiv:2506.08837, v1 2025-06-10)
- Type: paper (ETH Zurich and others, including Debenedetti and Tramer); HTML v3 read via fetch tool.
- Mechanism: six patterns: Action-Selector (LLM maps a request to a predefined action, tool outputs never feed back), Plan-Then-Execute (plan fixed before untrusted data is read), LLM Map-Reduce (isolated LLMs each read one untrusted item and emit a constrained output, e.g. yes/no), Dual LLM (privileged tool-using LLM never sees untrusted data; quarantined LLM with no tools reads it; results passed by reference), Code-Then-Execute, Context-Minimization. Principle: once an agent ingests untrusted input it must be constrained so that input cannot trigger consequential actions. The authors assume LLMs stay injectable, call guardrails heuristic and user confirmation burdensome and error-prone, and accept a utility cost.
- Evidence: design argument and case studies, not a benchmark. Companion benchmark result for CaMeL (abstract, item 4 in section 3): 77% of AgentDojo tasks solved with provable security vs 84% undefended.
- Applicability: the dispatcher is "an LLM that reads untrusted text and emits a constrained output", i.e. the quarantined role in Dual LLM and Map-Reduce; the fix is to constrain its output type (closed action set), not to sanitize its input.

### 2.11 Willison, "The lethal trifecta for AI agents" (2025-06-16) and Meta, "Agents Rule of Two" (2025-10-31)
- URLs https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/ ; https://ai.meta.com/blog/practical-ai-agent-security/ . Type: practitioner/vendor frameworks; both pages read via fetch tool.
- Mechanism: trifecta = private data + exposure to untrusted content + ability to communicate externally; Rule of Two = at most two of [A untrusted input] [B sensitive systems or data] [C change state or communicate externally] in one session; all three needs human-in-the-loop or a fresh-context handoff. Willison calls a 95% attack catch rate "a failing grade" for guardrail products.
- Evidence: argument, no measurements. Applicability: the dispatcher process alone has A only (no tools, no data), which is sound; what makes the system dangerous is the SINK: the draft text becomes a user-role message to an agent that has B and C. The question is not "does the dispatcher have tools" but "what can its output cause". A Level-1 human click is the Rule-of-Two human validation, and 2.2 says that validation degrades with volume. Auto-send via a Stop hook would complete the trifecta with nobody in the loop.

### 2.12 Olsen & Goodrich, "Metrics for Evaluating Human-Robot Interactions" (PERMIS 2003)
- URL https://faculty.cs.byu.edu/~mike/mikeg/papers/OlsenGoodrichPERMIS2003.pdf ; PDF text read by me. Type: HRI theory paper.
- Mechanism: neglect tolerance NT (how long an agent can be left alone), interaction effort IE (human time per interaction); robot attention demand RAD = IE/(IE+NT); free time FT = 1 - RAD; fan-out FO = 1/RAD = (IE+NT)/IE. The paper states that IE itself grows with fan-out (working-memory limits), so the plateau comes earlier than the formula says.
- Evidence: illustration with a simple simulated robot world, no field data. Applicability: the first-order model for "how many agents can one developer supervise" (F15); Agent HQ can measure NT and IE from its own transcripts (time agents run between asks; time from waiting to the next human message).

### 2.13 Mark, Gudith & Klocke, "The Cost of Interrupted Work: More Speed and Stress" (CHI 2008)
- URL https://www.ics.uci.edu/~gmark/chi08-mark.pdf ; PDF read by me. Type: lab experiment.
- Evidence: interruption context (related or not) did not change disruption cost; interrupted people finished faster with no quality difference but reported more stress, frustration, time pressure and effort. Applicability: a "needs you" ping costs the developer something even when the content is related to what they are doing; supports batching and fewer, better alerts. Weakness: lab task, short.

### 2.14 Adamczyk & Bailey, "If Not Now, When?" (CHI 2004)
- URL https://hci.rwth-aachen.de/materials/conferences/CHI2004/1p271.pdf ; PDF abstract and introduction read by me. Type: lab experiment.
- Evidence: interruptions delivered at model-predicted best moments (task boundaries) produced 56% lower annoyance than at worst moments and 43% lower than at random moments, with higher perceived respect for the primary task. Applicability: deliver non-urgent alerts at the human's own task boundaries; the "finished" class is naturally batchable.

### 2.15 Turan et al., "Oversight Has a Capacity: Calibrating Agent Guards to a Subjective, Fatiguing Human" (arXiv:2606.08919, v1 2026-06-08)
- Abstract page read only. Type: preprint (cs.AI), 2026.
- Evidence: 125 hand-labelled agent actions, Fleiss kappa 0.52 among reviewers on risk. Fatigue is a modelled endogenous variable; the inverted-U (safety peaks below full escalation) and flooding-attack results are model/simulation outputs, and the authors say they "motivate a human study". Applicability: the best available argument that an escalate-everything dispatcher can be less safe than a selective one, but it is not a human-subjects result; do not cite it as measured fatigue.

### 2.16 Li et al., "Last Step Matters: Early Uncertainty Cannot Predict Failure in Long-Horizon Agents" (arXiv:2608.29685, v1 2026-08-30, EMNLP 2026 main)
- Abstract page read only. Type: paper accepted at a main conference (as stated on the page).
- Evidence: on deep-research agent tasks verbal confidence predicts failure well at the end of a trajectory (mean AUROC 0.85) but no signal exceeds a mean AUROC of 0.60 at 50% progress; attributed to path switching. Applicability: self-reported confidence is informative at a turn boundary (what the dispatcher sees: a finished or waiting turn) and uninformative mid-run, so gating on end-of-turn confidence is on the favorable side of this result; a mid-run "stuck" intervention is not.

## 4. Findings

### Q1. The 93% figure and approval fatigue

F1 (VERIFIED). The 93% comes from one sentence in Anthropic's auto-mode engineering post (2.1): users accept 93% of manual permission prompts. A later Anthropic post gives 97% approved, 3% rejected, 39% of plans rejected (2.2). It is an acceptance rate over vendor telemetry with no stated sample, window or population. It is not a measure of whether reviewers looked. Prior in-repo claims: "MAST proves 93% rubber-stamping" REFUTED (the MAST abstract contains no such figure; the paper is a failure taxonomy of agent-to-agent traces); "developers approve ~93% of prompts without thorough evaluation" UNSUPPORTED as phrased (the source says accept, not "without evaluation"); "catch rates drop precipitously once a session exceeds 30 to 50 prompts" UNSUPPORTED as phrased, direction CONFIRMED (vendor study: human block rate about 17% early, about 5% after 50+ prior prompts).

F2 (VERIFIED as relayed, vendor-run). The only controlled evidence of vigilance decay on agent approvals is Anthropic's 1,053-tester study: humans caught 13.6% of injected dangerous commands (my Wilson interval from 143/1,053: about 11.7% to 15.8%, not from the source), auto mode 89%. Caveats: testers knew they were evaluated, no CIs, unreviewed, commands were "clearly dangerous". I found no peer-reviewed human-subjects study of fatigue in agent approvals (Turan 2606.08919 is a model plus 125 labels). Supporting but indirect: clinical alert fatigue (repeat alerts lowered acceptance about 30% each, Ancker 2017), automation bias not removable by training (Parasuraman & Manzey 2010), forcing functions help but are disliked (Buçinca 2021). INFERENCE: a one-click Accept button on LLM drafts is the pattern these results warn about, and Agent HQ shows it on every draft with a non-empty reply (2.8).

F3 (VERIFIED). Anthropic's own mitigation is not a better human prompt; it removes the prompt for the 97% via a classifier that is blind to assistant prose and tool results, plus a hard circuit breaker (3 consecutive or 20 total denials). Its honest miss rate is 17% on 52 real overeager actions (2.1). Even the best-resourced LLM gate on tool calls misses about one in six real overeager actions; a reply-drafting gate has no published number at all.

### Q2. Is self-reported confidence a valid gate?

F4 (INFERENCE from VERIFIED data and abstract-level literature). As a permission to send ("confidence at least 0.8, so send") it is not valid; as a veto ("below 0.8, so do not send") it is harmless and sensible. Evidence: (a) in Agent HQ's own log verbalized confidence takes 9 distinct values over 28 draws and 14 sit at or above 0.9, so it barely discriminates; (b) literature: verbalized confidence is overconfident and no method wins across tasks, with the white-box vs black-box AUROC gap only 0.52 to 0.61 (Xiong 2306.13063); calibration of "do I know this" transfers poorly to new tasks (Kadavath 2207.05221); for RLHF models verbalized confidence beats token probabilities but ECE only about halves (Tian 2305.14975); tool evidence such as web search drives agent overconfidence (2601.07264); mid-run confidence is near-useless (AUROC at most 0.60 at 50% progress) while end-of-turn is decent (0.85) (2608.29685); (c) reviewers disagree on what is risky (kappa 0.52, 2606.08919), so the target the confidence is meant to predict is noisy. In this log the gate bound only on the three R1 candidates, and there is no label to say whether blocking them was right.

F5 (VERIFIED computation). A false-send rate claim needs rated would-send drafts: to bound it at 5% with zero errors you need 59; 1% needs 299; 0.5% needs 598; one observed error adds about 60% to 90% more (table in section 0). Today n = 0, so no claim is possible, and the would-send rate is itself below roughly 10% (0/28), so the samples cannot be gathered by waiting; they need either a looser candidate definition measured in shadow, or implicit labels on all drafts (R1). A pre-registered sequential stopping rule is also required: stopping when the running count looks good inflates error.

F6 (INFERENCE, literature-backed). Better gate designs, in order of expected value for this fleet: (1) rule-first deterministic eligibility (structured waiting reason from hooks, closed action set, session not on hold, no side-effect tool in the last turn) so the LLM never sees the cases it cannot answer; (2) agreement across k=3 cheap samples on the same closed action (Xiong found consistency helps; semantic entropy and KnowNo-style sample disagreement are better uncertainty signals than a verbalized number), about $0.03 per draft; (3) a two-stage cheap-then-reasoning verifier as Anthropic does (stage 1 single token biased to block, stage 2 only when flagged) and as Trust or Escalate does (cheap judge first, stronger model on uncertainty, guarantee preserved); (4) a threshold chosen with Learn-then-Test or conformal risk control on logged labels, valid only if calibration labels are exchangeable with deployment, which agent workloads are not (new projects, new agents, drift); the 2026 trajectory-level CRC preprints are simulated or public-dataset results and none is a field study of an agent fleet; (5) logprob gating is unavailable through the CLI route (`claude --help` v2.1.331 has no logprobs option; whether the API exposes them I did not verify). LLM-as-judge reliability (over 80% human agreement, Zheng 2306.05685) is an average over preference pairs; its position, verbosity and self-enhancement biases make it weak evidence for a safety gate.

F7 (VERIFIED code). Calibration data design problem: `rate()` stores one verdict per draft only for drafts a human chooses to rate (selection bias), and no field records what the human actually did next. The audit has no ground truth from which to compute precision, recall or a risk-coverage curve, even if ratings start arriving.

### Q3. Prompt injection and confused deputy

F8 (VERIFIED code, INFERENCE on risk). The dispatcher converts untrusted text into trusted-channel text. Inputs: the agent's last reply and pending question (which can be derived from web pages, repos, tool outputs) and the user's last message. Output: a string that `/api/dispatch/send` delivers to an agent as a user-role message, i.e. with the developer's authority, to an agent with file, shell and network tools. This is the confused-deputy shape and a prompt-injection amplifier: an attacker who controls only a web page can, via the agent's reply, steer the dispatcher's draft, and the draft arrives as if the developer wrote it. By the Rule of Two the dispatcher process is safe (A only: `--tools ""`, empty MCP, no settings sources) and the system is not (the sink has B and C). Today the barrier is one human click; there is no auto-send path (2.8). That barrier is weak by F2.

F9 (VERIFIED/INFERENCE). Assessment of the current mitigations:
- No tools, no MCP, no settings, temp cwd: adequate, and stricter than ccmanager's helper (2.5). Keep.
- XML-like data tags plus "treat as data": inadequate as a boundary. Delimiting is the variant the spotlighting authors discourage (2.9); the tags are not escaped, so a forged `</agent_reply>` ends the data region; the model also receives the standing policy in the same message, so a forged close tag can add fake rules; and adaptive attackers beat 12 published defenses of this class above 90% on most (Nasr 2510.09023; Willison: 95% is a failing grade). Cheap to improve (datamark, random boundary, policy only in the system prompt) but still only a speed bump.
- Regex hints: inadequate. Three word-lists (money, legal, credentials). Not covered: destructive git, publish, install, network fetch, exfil, secrets in diffs. The 13+ allowlist-bypass CVEs in Claude Code (2.4) show regexes over command text fail even with expert maintenance.
- `alwaysHuman` list: enforced only by the same model that is being attacked (`needs_human` is a model output). Inadequate as a control; fine as a prompt hint.
- Rate limits: inadequate. Counted only for past would-sends; the loop check is exact equality; no global budget on sends; the 150/day cap counts failures (section 0).
- Confidence 0.8 and rule id: attacker-influenceable model outputs (JudgeDeceiver shows LLM judges can be steered by optimised text, 2403.17710).
- Missing: a closed output set, revalidation at send time, drafts bound to the waiting turn, visible provenance of the text for the human, a fail-closed path when the dispatcher errors.
Verdict: acceptable for draft-only with a human reading before clicking; not acceptable for any automatic send path.

F10 (VERIFIED). Agent HQ's input policy is the opposite of the two production auto-reviewers I read. Claude Code's classifier strips tool results and does not see assistant prose; the Codex Guardian scores structured actions with a separate authorization field and a stale-score guard. Agent HQ gives the model the agent's prose, which is where an injected instruction first lands.

F11 (VERIFIED). Defects in the send path that matter for safety (2.8): ReferenceError after delivery (`sentText`), webhook GET with side effects, default public HMAC secret, decision-independent accepted token, no expiry, literal "Approved" fallback, draft lookup by session id rather than by waiting turn. The in-repo "15-minute expiration" claim is REFUTED for 86169e7. If the webhook is exposed beyond localhost, anyone who knows the public source can forge an approval for any session id they learn.

Other tools decide on structured, pre-execution data: Claude Code rules plus PreToolUse/PermissionRequest hooks (deny, then ask, then allow; hooks cannot override deny rules; a hook can even answer AskUserQuestion), `--permission-prompt-tool` for headless runs, and an LLM classifier on tool calls that never sees tool results (2.1, 2.3); Codex untrusted/on-request/granular/never plus a Guardian reviewer with categorical risk and a separate authorization signal (2.6); Gemini CLI a TOML policy engine with allow/deny/ask_user and tier priority, ask_user = deny when non-interactive (item 39); ccmanager a regex blocklist then a Haiku binary yes/no that sends Enter, fail-closed (2.5). For the 19 finished-turn drafts the model chose "send nothing" 16 times and `continue` 3 times; all 9 other drafts were escalated and none was answered. So "which class dominates wait time" is NOT MEASURED. The in-repo "16 of 19 agents waiting idle for answers" is UNSUPPORTED (no source or log in the repo; the audit has no concurrent snapshot). ### Q5. Notification and queueing for a fleet

F15 (VERIFIED math, HYPOTHESIS parameters). Human-as-server model. N agents each work for mean Z minutes, then need the human for mean S minutes; one human serves one request at a time (finite-source M/M/1, exact solution computed by me with a script; exponential times and FIFO assumed). Human utilisation U = 1 - P0 with P0 = [sum over k of N!/(N-k)! (S/Z)^k]^-1; throughput X = U/S; mean wait before service = N/X - Z - S; saturation point N* = (Z+S)/S (equals Olsen-Goodrich FO = (IE+NT)/IE). Z and S below are placeholders, not measured:

| Z (work between asks) | S (human time per ask) | N* | N=6 | N=12 | N=20 |
|---|---|---|---|---|---|
| 15 min | 1 min | 16 | U 37%, wait 0.4 min, agent efficiency 91% | U 69%, wait 1.4 min, 86% | U 95%, wait 5.0 min, 72% |
| 15 min | 3 min | 6 | U 81%, wait 4.3 min, 67% | U 100%, wait 18 min, 42% | U 100%, wait 42 min, 25% |
| 30 min | 3 min | 11 | U 52%, wait 1.9 min, 86% | U 88%, wait 7.9 min, 73% | U 100%, wait 27 min, 50% |
| 10 min | 2 min | 6 | U 81%, wait 2.8 min, 67% | U 100%, wait 12 min, 42% | U 100%, wait 28 min, 25% |

Reading: beyond N* throughput is flat at 1/S requests per unit time (20 per hour when S=3 min) and extra agents only add idle waiting; agent efficiency falls toward 1/N. A fleet of 7 to 19 agents (the brief's range) is below saturation only if S is about 1 minute or Z is 30+ minutes. If interaction effort grows about 4% per extra agent (HYPOTHESIS, following Olsen & Goodrich's own caveat), with Z=15 and S0=2, throughput peaks near N=10 (21.4 requests per hour) and then declines (17.0 at N=20), so adding agents past the peak reduces useful output. Cummings & Mitchell (item 28) found that modelling wait time and lost situation awareness cut predicted operator capacity 36% to 67% in simulation, the same direction.

F16 (VERIFIED math). What a triage layer can change: removing a fraction f of asks entirely (perfect, free) at N=12, Z=15, S=3: f=0.4 lowers wait from 18 to 10 min and raises agent efficiency 42% to 65% (relative to the longer cycle). Shrinking S for a covered share g of asks via one-click accepted drafts (S from 3 to 1): g=0.5 gives S_eff 2.0, throughput 19.9 to 28.9 requests per hour, wait 18 to 8 min. Break-even for auto-handling: net minutes saved per auto-handled item = (1-p)S - pC, so the false-send rate must stay below p* = S/(S+C). With S=1 and C=15 min cleanup, p* = 6.3%; S=0.5, C=30: 1.6%; S=3, C=60: 4.8%. Compare section 0: demonstrating p below 5% needs 59 error-free rated sends, so a dispatcher can be net-negative long before it is demonstrably safe when cleanup is expensive. The benefit is largest for asks with large S and low risk, not for the common finished-turn class where the right reply is nothing.

F17 (VERIFIED theory + lab evidence; INFERENCE for application). Ordering: shortest-remaining-processing-time minimises mean response time in a single-server queue (Schrage 1968; secondary confirmation only); with different costs of delay the weighted version (the classical c-mu / Smith rule: serve in descending order of delay-cost rate over expected service time; textbook result, not re-verified in this session) fits "blocking-ness": an agent idle on the critical path has a high delay cost, a finished background task a low one. Starvation needs an age cap or deadline override. Timing and channel: interruptions at task boundaries cost much less annoyance (Adamczyk & Bailey 2004: 56% and 43% lower than worst and random moments; Iqbal & Bailey 2008 breakpoint deferral lowered frustration); any interruption costs stress and effort even when related (Mark 2008); batching to three times a day helped well-being in a phone study (Fitz 2019, search-result level, different task); repeated alerts for the same item are accepted less (Ancker 2017). INFERENCE for Agent HQ: ambient state (office view, tray count) for working and for finished-and-reviewable; alert (sound, toast) only for blocked-and-high-delay-cost; batch finished turns into a digest delivered at the developer's own breakpoint; never re-alert for the same turn.

F18 (VERIFIED code). Agent HQ does not record the two quantities the model needs, Z (time agents run between asks) and S (human time per ask), nor the time from a session entering waiting to the next human message. Transcripts contain them (state transitions and next user-message timestamps), so they can be computed offline without new instrumentation.

## 5. Recommendations for Agent HQ (ranked)

R1. Fix reliability and measurement before any gating work. (Expected benefit: high, unblocks everything. Evidence: own data, VERIFIED. Effort: S. Failure modes: none material.) (a) Store the full CLI stdout JSON (`result`, `api_error_status`, `is_error`), exit code and stderr, not 300 chars. (b) Do not count errors toward `maxDraftsPerDay`, and do not store an error as a completed draft; retry with backoff and add a circuit breaker (stop drafting for 15 min after 3 consecutive zero-token results; show "dispatcher offline" in the UI) so a limit window cannot burn the cap or flood the log (148 errors in one hour on 11-21). (c) Truncate from the head and keep the tail (or both ends) of agent text instead of keeping only the first N characters. (d) Fix `sentText`. (e) Log implicit labels for every draft: the next human message after the waiting turn (from the transcript adapter), classified exact match / edited / different / none, plus the time from waiting to that message by class. Measure: drafting success above 98% over a week; a label-agreement table per class; the Z and S distributions for F15.

R2. Replace LLM waiting-reason labelling with structured hook signals for Claude Code sessions. (Benefit: exact causes, removes the injection surface for that decision, sees the permission-prompt population Agent HQ is blind to today. Evidence: docs 2.3, VERIFIED. Effort: M. Risk: an install step in user `settings.json` which only the owner changes; hook exit-code semantics.) Use Notification (`permission_prompt`, `idle_prompt`, `agent_needs_input`, `agent_completed`), Stop (`last_assistant_message`) and PermissionRequest events (an HTTP hook to `127.0.0.1:7787`) to write a `waiting_reason` field; keep the transcript tail as fallback and for Antigravity and Codex. Measure: fraction of waiting turns with a structured reason; agreement with the LLM label in a one-week shadow run.

R3. Make triage ordering and batching the product, not reply drafting. (Benefit: addresses the queueing bottleneck directly. Evidence: F14 and F15 to F17, theory plus lab studies, INFERENCE for transfer. Effort: M. Failure modes: starvation of low-weight items, wrong delay-cost weights.) Sort the Needs-You queue by weight over expected human minutes (blocked and cheap first; add an age cap); show estimated human minutes per item; put finished-turn items into a digest rather than alerts; add a work-in-progress limit (warn, or refuse to start agent N+1, when predicted wait from the F15 model with measured Z and S exceeds a threshold such as 5 minutes). Measure: median and p90 time from waiting to human response per class; agent efficiency E = running time / (running + waiting) before and after.

R4. Harden the dispatcher pipeline now (applies even in draft-only mode). (Benefit: closes the confused-deputy path. Evidence: F8 to F11, 2.9 to 2.11. Effort: S to M. Risk: some loss of draft usefulness.)
 1. Closed output set: the model picks a `reply_id` from a fixed list (for example continue, run the tests, yes proceed, no stop, show me the diff) plus optional fixed-vocabulary slots; the reply string is produced by code from a template, never by the model. This is the Action-Selector/Map-Reduce pattern (2.10) and removes free-text injection output; keep a free-text "suggestion" visible to the human but never sendable in one click.
 2. Input hygiene: datamark untrusted fields and use a fresh random boundary per call; strip or neutralise tag-like `<` sequences in untrusted text; keep policy and the alwaysHuman list only in `--system-prompt` (SYSTEM already separate) so untrusted text never sits next to rule text; pass the tail of the agent message plus the structured ask. A speed bump only (F9).
 3. Deterministic pre-gate before the model, fail closed: if the last turn used a side-effect tool class (git push or force, rm, publish, install, curl/wget, deploy) or its text matches the three existing regex classes extended with destructive, network and secret patterns, the draft is `needs_human` and no reply is offered. ## 6. Rejected or not applicable

- "MAST proves 93% rubber-stamping" and any use of MAST for approval statistics: wrong paper.
- Auto-send through the planned Stop hook (dispatch.js L149) at this commit: 0 of 28 would-send, 0 ratings, the sink completes the trifecta, and drafting reliability is 12%. Not before R1, R4, R5.
- Verbalized confidence at 0.8 as the safety gate, and "raise the threshold to 0.9": 14 of 28 draws already sit at or above 0.9.
- Logprob or token-probability gating through `claude -p`: the CLI exposes no logprobs; unverified for the API.
- Conformal prediction / CRC as the first step: needs exchangeable calibration data of a few hundred labels per stratum and a stationary workload; the 2026 CRC-for-agents papers are preprints with simulated or public-dataset experiments. Use plain exact binomial bounds until labels exist, then Learn-then-Test.
- An LLM judge or injection-detector classifier as the primary defense: adaptive attacks exceed 90% on published defenses (2510.09023), optimisation attacks steer LLM judges (2403.17710), Willison's "95% is a failing grade". Fine as an extra layer, not a boundary.
- Spotlighting by base64 encoding for Sonnet-class reply triage: gains shown only on 2024 GPT models, harmful to weaker ones; datamarking is enough for a speed bump.
- A large regex or command-syntax allowlist built in Agent HQ: Anthropic's own engine has had 13+ bypass CVEs; use closed reply sets and the vendor's engine.
- Batching "three times a day" from Fitz 2019: a well-being study about phone notifications, not blocking agents; use breakpoints and class-based digests instead.
- Treating Turan et al.'s inverted-U fatigue curve as measured: it is a model result.
- Treating the queueing results as precise predictions: exponential times, FIFO, constant S and independence are simplifications; use the model for shape and break-even, and measure Z and S.
